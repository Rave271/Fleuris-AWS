Fleuris Vault – Low-Level Design (LLD)

1. Introduction & Purpose

Fleuris Vault is a secure digital banking demo platform built with Flask, SQLite, and Jinja templates. It demonstrates robust security controls, including password hashing, CSRF protection, brute-force lockout, audit logging, and role-based access control, following OWASP best practices. This LLD details the internal structure, data flows, security mechanisms, and deployment specifics for maintainers and auditors.

2. Technology Stack

  • Backend: Python 3.12, Flask 2.3
  • Database: SQLite (local file bank.db)
  • Frontend: Jinja2 templates, HTML, CSS
  • Security: Werkzeug password hashing, pyotp (MFA), qrcode (MFA QR), custom security headers
  • Deployment: Gunicorn (Procfile), Render.com ready

3. High-Level Architecture Diagram

User Browser → Flask App (app.py) → [Templates, DB, Static, Security Log]
  • All HTTP(S) requests are routed through Flask, which handles authentication, session, and security logic.
  • Templates are rendered server-side using Jinja2.
  • All persistent data is stored in SQLite; security events are also logged to a file.

4. Detailed Module Breakdown

4.1 Flask App Structure (app.py)

  • App Initialization: Sets up Flask app, secret key, session config, logging, security headers.
  • Database Connection: get_db() opens SQLite connection per request, close_connection() closes on teardown.
  • Security Headers: add_security_headers() injects CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy into every response.
  • Logging: Python logging writes to security.log and DB table security_events.
  • CSRF Protection: csrf_token() generates session-bound CSRF token; require_csrf_token() validates on POST.
  • User Session Management: current_user() returns user row from session; login_required() decorator for protected routes.
  • Route Handlers:
    • / – Home page
    • /login, /logout, /mfa-setup – Authentication and MFA setup
    • /dashboard – User/admin dashboard with role-based content
    • /transfer – Customer money transfer (CSRF, balance, recipient checks)
    • /statement, /statement/<id> – Account statements (role/ownership checks)
    • /users, /admin/users/<id> – Admin user management, unlock, detail
    • /security, /security-log – Admin security center/log (DB/file)
    • /security-demo, /demo-controls – Demo & controls for security features
  • Error Handlers: Custom 400, 403, 404, 500 error pages.
  • Database Initialization: init_db() creates tables, seeds demo users, ensures schema.

4.3 Security Features (with Implementation Details)

  • Password Hashing: Uses werkzeug.security.generate_password_hash and check_password_hash. No plaintext password storage; legacy column is nulled.
  • Brute-force Lockout: On failed login, failed_login_count incremented. After 5 failures, locked_until set to 10 minutes in future. Login checks locked_until before allowing authentication.
  • CSRF Protection: csrf_token() generates a random token per session. All POST forms include hidden CSRF token field. require_csrf_token() aborts with 400 if token missing/invalid.
  • Security Headers: Set via after_request for every response. CSP restricts sources, X-Frame-Options DENY, etc.
  • Audit Logging: log_event() writes to both security.log and security_events table. All sensitive actions (login, transfer, access denied) are logged.
  • Access Control: Role checks for admin/customer on all sensitive routes. Ownership checks for statement access. 403 error and event log on violation.
  • MFA (TOTP): Users can enable TOTP via /mfa-setup. QR code generated for authenticator apps. Login requires TOTP code if enabled.

4.4 User Roles & Access

  • Customer: Can view dashboard, transfer funds, view own statement. Cannot access admin or other users' data.
  • Admin: Can view all users, unlock accounts, view all statements, security events, logs, and demo controls. Cannot perform transfers or view own statement.

5. Data Flow Diagrams

5.1 Login Flow

  1. User submits username, password (and MFA code if enabled).
  2. System checks for lockout (locked_until).
  3. Password hash verified.
  4. If TOTP enabled, code is verified.
  5. On success: session set, failed count reset, event logged.
  6. On failure: failed count incremented, lockout if needed, event logged.

5.2 Transfer Flow

  1. Customer selects recipient, amount, description.
  2. CSRF token validated.
  3. Recipient and amount validated (not self, within limits, sufficient balance).
  4. If review step, show confirmation.
  5. On confirm, balances updated, transaction inserted, event logged.

5.3 Admin Unlock Flow

  1. Admin selects user to unlock.
  2. CSRF token validated.
  3. failed_login_count and locked_until reset.
  4. Event logged.

7. Deployment & Environment

  • requirements.txt: Flask, gunicorn, pyotp, qrcode, Pillow.
  • Procfile: Gunicorn start command.
  • runtime.txt: Python version pin.
  • RENDER_DEPLOYMENT.md: Render.com setup guide.
  • Environment: AEGIS_SECRET_KEY required for session security.
  • Database: SQLite file auto-initialized on first run.

8. Security Considerations (Expanded)

  • All user input is parameterized in SQL (no string interpolation).
  • Session cookies are HTTPOnly, SameSite=Lax, 30 min expiry.
  • Security events and log file for audit and forensics.
  • MFA available for all users, enforced if enabled.
  • No plaintext password storage; legacy column nulled on migration.
  • Admins cannot perform customer actions (transfers, statements for self).
  • Customers cannot access other users' data or admin routes.
  • All sensitive actions (login, transfer, unlock, access denied) are logged.
  • Security headers enforced for every response.
  • Demo controls allow safe testing of lockout, seeding, and event clearing.
